# OUTREACH INTELLIGENCE TOOL
## Specifica Funzionalità
### Per Luca Nesler & Stefano — Aprile 2026

---

## Panoramica

Tool locale (Ubuntu) per gestire l'outreach B2B di Luca e Stefano come speaker/formatori. Non è un CRM passivo: è un sistema di intelligenza che impara dai risultati, adatta la strategia, e scopre proattivamente nuove opportunità.

**Stack:** Streamlit + SQLite + Claude API (Sonnet 4.6) + Folium
**Utente:** Singolo (Stefano)
**Lingua interfaccia:** Italiano
**Ciclo d'uso:** Mensile (discovery + batch email), con gestione follow-up continua

---

## FASE 1: MVP

Obiettivo: sistema funzionante per il ciclo mensile discovery → email → tracking.
Stima: 30-45 ore di sviluppo con Claude Code.

---

### 1.1 Database Venue

Il cuore del sistema. Ogni venue è un record con metadati ricchi.

**Dati per ogni venue:**
- Nome, tipo (Rotary, Lions, fiera, coworking, associazione, banca, università, hub innovazione...)
- Indirizzo fisico, città, provincia, regione
- Coordinate GPS (per la mappa)
- Edificio/struttura ospitante (es. "NOI Techpark", "Fiera Bolzano", "Parkhotel Laurin")
- Email di contatto, sito web, canali social (Instagram, Facebook, LinkedIn)
- Lingua prevalente (IT, DE, EN, bilingue)
- Tipo di finanziamento/natura (pubblico, privato, associazione, cooperativa)
- Angolo consigliato (storytelling puro, AI + storytelling, AI puro, collaborazione)
- Note libere
- Tag/categorie per clustering (assegnati dall'LLM, modificabili manualmente)
- Deadline note (es. "Call for speakers chiude 30 giugno 2026")
- Data di creazione nel sistema
- Fonte della scoperta (importato da documento, scoperto da LLM, aggiunto manualmente)

**Import iniziale:** Le ~50 venue dai due documenti markdown esistenti vengono importate automaticamente all'avvio, con parsing dei metadati già presenti (email, contesto, angolo).

---

### 1.2 Database Contatti

Ogni persona con cui si comunica è un record separato, collegato a una o più venue.

**Dati per ogni contatto:**
- Nome, cognome, ruolo/titolo
- Venue di appartenenza (relazione many-to-many: una persona può essere in più venue)
- Email, telefono, profili social
- Lingua preferita
- Tono consigliato dall'LLM (formale, cordiale, informale, tecnico)
- Interessi/topic rilevanti (assegnati dall'LLM in base alle interazioni)
- Note libere
- Storico interazioni (collegato al tracker, vedi 1.3)

---

### 1.3 Outreach Tracker

Traccia ogni interazione su qualsiasi canale.

**Per ogni interazione:**
- Data e ora
- Canale (email, DM Instagram, DM LinkedIn, DM Facebook, telefono, di persona, altro)
- Direzione (inviata / ricevuta)
- Venue collegata
- Contatto collegato
- Tipo (prima mail, follow-up 1, follow-up 2, risposta, risposta automatica, proposta meeting, rifiuto, altro)
- Contenuto: testo completo (incollato manualmente da Stefano)
- Draft originale dell'LLM (se diverso dalla versione inviata, entrambi vengono salvati)
- Stato pipeline della venue dopo questa interazione (da contattare, contattata, risposta ricevuta, meeting fissato, presentazione confermata, completata, rifiutata, nessuna risposta)

**Flusso operativo:**
1. LLM genera draft → Stefano lo rivede → Stefano invia da Aruba/social → Stefano incolla nel tool la versione inviata
2. Quando arriva risposta → Stefano la incolla nel tool
3. LLM analizza la risposta e propone azione successiva (follow-up, cambio approccio, contatto diverso, nuovo canale)

---

### 1.4 Profili Speaker

Due profili persistenti nel sistema, aggiornabili.

**Per ogni speaker (Luca, Stefano):**
- Bio completa (inserita da file/testo)
- Competenze chiave (storytelling, AI, automazione, marketing, narrativa...)
- Esperienze rilevanti (libri, formazione, collaborazioni aziendali, festival...)
- Lingue
- Ruolo nella coppia (chi presenta cosa, chi è lead su quale topic)

**Logica LLM per i profili:**
- In base alla venue, l'LLM decide: proporre solo Luca, solo Stefano, o entrambi
- In base alla venue, l'LLM decide: quali competenze sottolineare di ciascuno
- Regola: se la venue è fortemente AI-oriented → evidenziare Stefano e le sue competenze di automazione. Se è marketing/comunicazione oriented → lead con Luca e storytelling. Se è mista → proporre entrambi
- L'LLM non applica regole rigide: usa il contesto completo (tipo venue, interessi del contatto, risposte passate da venue simili) per decidere

---

### 1.5 Generazione Email/Messaggi con LLM

Il tool non si limita a tracciare: genera i draft.

**Draft prima mail:**
- L'LLM riceve: profilo venue, profilo contatto, profili speaker, storico interazioni con venue simili, angolo consigliato
- Produce: oggetto + corpo mail in italiano (o inglese/tedesco se la venue lo richiede)
- Decide: chi proporre come speaker, quale angolo usare, quale tono, quanto essere diretti
- Stefano rivede, modifica se necessario, invia manualmente

**Draft follow-up:**
- L'LLM riceve: tutto il contesto sopra + la mail effettivamente inviata (non il draft) + la risposta ricevuta (o l'assenza di risposta)
- Propone: timing del follow-up (es. "7 giorni per un Rotary, 4 giorni per una fiera con deadline vicina")
- Stefano conferma o aggiusta il timing
- L'LLM genera il draft del follow-up contestualizzato

**Suggerimento canale:**
- Per ogni venue/contatto, l'LLM suggerisce il canale migliore per il primo contatto e per i follow-up
- Es: "Per questa venue l'email è il canale giusto" oppure "Questo contatto è molto attivo su LinkedIn, considera un DM dopo la mail"
- Se il canale è social, l'LLM drafta anche il messaggio social (più breve, tono diverso)

---

### 1.6 Discovery Venue con LLM

Ciclo mensile: Stefano lancia la discovery, l'LLM cerca nuove venue.

**Input della discovery:**
- Scope geografico selezionato da Stefano (provincia / regione / regioni limitrofe / tutta Italia)
- Database venue esistenti (l'LLM sa cosa è già stato contattato)
- Profili speaker (l'LLM sa cosa Luca e Stefano offrono)

**Output della discovery:**
- Lista di venue nuove con metadati compilati dall'LLM (nome, tipo, email, sito, città, regione, angolo consigliato, deadline se presenti)
- Per venue già note: segnalazione di nuovi eventi o opportunità (es. "Klimahouse 2027 ha aperto la call for speakers")
- Prioritizzazione: venue con deadline ravvicinate in cima
- Stefano rivede, conferma le venue da aggiungere al database, scarta quelle non rilevanti

**Meccanismo:** Claude API con web search integrato. L'LLM cerca su directory italiane (rotary.org/it, lions.it, unioncamere.gov.it, fiereitaliane.it, italiancoworking.it, siti regionali, calendari eventi) e filtra per rilevanza rispetto ai profili speaker.

---

### 1.7 Mappa Geografica

Visualizzazione della copertura territoriale.

**Funzionalità:**
- Mappa Italia con venue posizionate (marker colorati per stato: contattata, risposta, confermata, ecc.)
- Evidenziazione province/regioni coperte vs scoperte
- Filtri: per tipo venue, per stato pipeline, per angolo
- Utile sia per capire dove si è già presenti sia per guidare la discovery ("cerca in Veneto, non abbiamo nulla lì")

**Implementazione:** Folium + GeoJSON regioni/province italiane (open data openpolis).

---

### 1.8 Intelligenza Cross-Venue (Clustering)

L'LLM non tratta ogni venue come caso isolato.

**Come funziona:**
- L'LLM assegna tag/categorie a ogni venue (topic, settore, dimensione, tipo pubblico, lingua, formalità)
- Quando drafta una mail per una venue nuova, consulta lo storico di venue con tag simili
- Se una mail con angolo "AI + automazione" ha avuto tasso di risposta alto su venue tipo "hub innovazione", l'LLM lo considera
- Se il contatto di una venue è la stessa persona di un'altra venue, l'LLM lo rileva e adatta (non mandare due mail identiche alla stessa persona per due venue diverse)
- Se due venue sono nello stesso edificio (es. NOI Techpark ospita sia AI Breakfast che SFScon), l'LLM lo sa e ne tiene conto

**Nota:** nel MVP il clustering è basato su tag semplici assegnati dall'LLM. Non serve ML complesso.

## FASE 2: VERSIONE COMPLETA

Obiettivo: aggiungere le funzionalità avanzate dopo aver validato il MVP per 2-4 settimane.
Stima aggiuntiva: 40-70 ore di sviluppo con Claude Code.

---

### 2.1 Ingestion Slide/Presentazioni

Il tool ingesta le presentazioni usate con le venue.

**Funzionalità:**
- Upload di file PPTX/PDF delle presentazioni fatte o preparate
- L'LLM estrae i punti chiave e li associa al profilo speaker e/o alla venue
- Quando una venue risponde proponendo un meeting, l'LLM suggerisce: quale set di slide usare come base, cosa modificare per adattarlo alla venue specifica, quali punti enfatizzare
- L'LLM usa il contenuto delle slide per scrivere email più precise ("nella nostra presentazione mostriamo come..." diventa specifico, non generico)
- Le slide vengono taggate per tipo (presentazione completa, pitch 10 slide, case study, workshop outline)

---

### 2.2 Dashboard Interna per LLM

Non una dashboard visuale per Stefano, ma un contesto strutturato che l'LLM consulta prima di ogni decisione.

**Metriche tracciate internamente:**
- Tasso di risposta per tipo venue, angolo, canale, lingua, regione
- Tempo medio di risposta per tipo venue
- Angoli che convertono meglio (AI vs storytelling vs misto)
- Contatti che rispondono vs contatti che ignorano (per tipo ruolo: presidente, segretario, ufficio formazione, marketing manager)
- Venue che portano a meeting vs venue che restano a livello email
- Follow-up che funzionano vs quelli ignorati

**Come l'LLM le usa:**
- Prima di draftare una mail, l'LLM consulta queste metriche
- "Le venue tipo 'associazione di categoria' rispondono meglio con angolo misto e tono formale. Le venue tipo 'coworking' rispondono meglio con angolo AI e tono informale."
- Le metriche non sono rigide: l'LLM le usa come prior, non come regola

---

### 2.3 Discovery Automatica Schedulata

Evoluzione della discovery manuale del MVP.

**Funzionalità:**
- Possibilità di schedulare la discovery (es. primo lunedì del mese)
- Notifica a Stefano con il report delle venue trovate, pronte per la revisione
- Monitoraggio deadline: il tool avvisa se una deadline si avvicina (7 giorni prima, 3 giorni prima)
- Monitoraggio venue già contattate: se un sito pubblica un nuovo evento, il tool lo segnala

---

### 2.4 Export e Backup

**Funzionalità:**
- Export completo database in JSON/CSV (per backup o migrazione)
- Export singola venue con tutto lo storico (per condividere con Luca)
- Backup automatico SQLite (cron job locale, giornaliero)

---

## Architettura Tecnica

**Frontend:** Streamlit (locale su Ubuntu, nessun deploy remoto necessario)
**Database:** SQLite (singolo file, backup semplice, performance più che sufficiente per centinaia di venue)
**LLM:** Claude API (Sonnet 4.6) con web search per discovery
**Mappa:** Folium + GeoJSON Italia (openpolis/geojson-italy)
**Slide parsing:** python-pptx per PPTX, PyMuPDF per PDF (Fase 2)
**Costo mensile stimato:** €15-20 (API Claude per ~50 email/mese + 1 discovery run + follow-up)

**Nessuna integrazione email:** Il tool non invia email. Drafta il testo, Stefano lo copia e lo invia da Aruba webmail o dal canale social appropriato. Poi incolla nel tool la versione inviata e le risposte.

---

## Flusso Operativo Mensile

```
1. DISCOVERY (1 volta/mese)
   Stefano seleziona scope geografico → Lancia discovery
   → LLM cerca venue nuove + nuovi eventi su venue note
   → Stefano rivede e conferma le venue da aggiungere

2. BATCH EMAIL (stesso giorno o giorno dopo)
   Per ogni venue confermata:
   → LLM genera draft (prima mail o follow-up)
   → Stefano rivede e modifica se necessario
   → Stefano invia da Aruba/social
   → Stefano incolla la versione inviata nel tool

3. GESTIONE RISPOSTE (continuo)
   Quando arriva risposta:
   → Stefano la incolla nel tool
   → LLM analizza e propone azione successiva
   → Se serve follow-up: LLM propone timing + draft
   → Stefano conferma timing, rivede draft, invia

4. REVISIONE (fine mese)
   → LLM aggiorna tag/clustering in base ai risultati
   → Metriche interne aggiornate
   → Pronto per il ciclo successivo
```
